# Decisions

Each entry says what we did first, then why we did it.

1. organize and centralized the whole evaluation harness.
2. prompt the harness to be minimalistic, no backend logic and how i want the UI to appear. objective is to at least be able to visualize all the ai written questions, answer keys. this is to make sure the questions are hard and realistic, answer keys are verified manually by human.
3. put question marks UI to inform us on each component, what they means to answer where and what the number means
4. organize the eval harness to 3 tabs: dashboard, evaluate and visualize. Visualise enable humans to visualize the questions, answer keys. able to edit unverified answer keys and AI written questions can be added too
5. Committed the existing dashboard work on a new local branch, `calvin-feat-evaluation-overnight`. We did this so a pull cannot remove the work again, and so the shared branch with Bao Sheng stays untouched until you review it.
6. Set the rules for the overnight work: fix the evaluation first and build React second, change only `evaluation/` and never `apps/api`, and use at most about 500 Groq calls. We fix first because React only displays the scores, so the scores must be trustworthy before we display them nicely.
7. Recorded the model's raw draft and the exact reason for every blocked answer in each run. We did this because the app only wrote those reasons to a log, so nobody could see why students got no answer.
8. Found why almost every Groq answer was blocked: the model gave a valid quote for all 20 citations, but it left the `[1]` markers out of the answer text (one answer used `【5】` instead). The check treated this as a failure, so 0 of 15 answers reached the student. This is a format failure and not a knowledge failure, and no stage score could show it.
9. Re-ran the evaluation on the finalized labels. We did this because every earlier score used the old labels. Test Hit@5 dropped from 0.971 to 0.912, so the old number was too high.
10. Changed the goal of the overnight work: find and define every concern, and do not try to solve them yet. We dropped the pipeline variants and proposals because the team will write its own questions, and those questions need a harness that shows problems clearly.
11. Scheduled a wake-up for 6:15am. We did this so the work can continue if tokens run out before the 6:10am reset.
12. Added 30 hard student questions: vague, typos, Manglish, "explain like I'm 12", questions that need two parts of the notes, and 5 questions the notes cannot answer. A Sonnet agent wrote them, and we marked every row unverified and report it separately. We did this because the 50 AI questions are clean and polite, while real students are not, and nothing tested whether the app can say "I don't know".
13. Built one question set that covers all four PDFs. We did this because the team will write questions on every PDF, and because searching four PDFs is harder and closer to real use than searching one.
14. Gave each teammate their own question file in `datasets/cpt316/team/`, and added a merge script that joins them with the original questions. The script checks that every gold quote really appears on its page, and lists any row it skips. We did this so people do not overwrite each other in git, and so a typo in a quote is caught before it quietly lowers a score.
15. Added a "Human-written only" option to Export. We did this so the team can share only their own questions, without the 50 AI questions.
16. Defined 14 concerns in `concerns.md`, and wrote code that measures each one after every run. Each concern says what the student feels, how we measure it, and what a bad result looks like. We did this because the stage scores looked good while students got no answer at all, so we now name each hidden problem and give it a number.
17. Used a second AI model, `qwen`, as a judge to grade every answer for correctness, support and usefulness. It comes from a different company than the model that writes the answers, and it also grades answers that were blocked. We did this because a model grading its own work is too kind, and because we need to know how many good answers were thrown away.
18. Labelled every judge number "AI judge, not yet checked by a human", and marked a concern "partly measured" when some answers were not judged. We did this because the judge is not yet proven, and a half-finished check must not look complete.
19. Made the dashboard tests work on any computer. We did this because they expected exactly 3 runs, so they failed on any machine with a different number of local runs, even when the code was fine.
20. Rebuilt the dashboard in React as a new app, `apps/evaluation`, run with `pnpm dev:evaluation`. It has the same three tabs and features, and reuses the buttons, dialogs and PDF viewer of the main app. We did this because the old page had grown to about 2,400 lines of hand-written page updates, which made every new feature slow and risky. We kept the old dashboard for now, so nothing breaks while the team moves over.
21. Kept the same saved-data keys and the same export file format in the React app. We did this so edits already saved in the browser, and files exported from the old dashboard, still work in the new one.
22. Added a Concerns section to the React dashboard: one card per concern, worst first, and a click on an example opens that question beside its PDF. We did this so the team sees the hidden problems first, not only the stage scores.
23. Added two optional settings to the shared PDF viewer in `packages/ui`. This is the only change outside `evaluation/` and `apps/evaluation`, and pages that do not use the settings work as before. We did this so a quote can scroll into view inside the PDF pane without moving the whole page.
24. Split the harness into a stable part and a moving part. The stable part is the question format, the run output format, the run loop, and the screen for reading a question beside its PDF, and we build these carefully once. The moving part is concerns, scorers, the judge, and the variants we compare. Each one becomes a small Python file that writes columns into one results table, and we explore that table in a notebook or spreadsheet, not in new React screens. We did this because every new concern or score needed new hand-written UI. The old dashboard grew to about 2,400 lines this way, and the React app was starting to grow the same way, even though these parts change every week.
25. Made question edits save straight to each person's file, `datasets/cpt316/team/<name>.json`, instead of only to the browser. The save is safe: it writes a temp file, flushes it to disk and then swaps it in, it refuses to save if the file changed since the page loaded, and it refuses a file with the same question id twice. New question ids start with the person's name, and the merge now keeps human reviews and the hard-case flag. We did this because clearing the browser lost all human annotation work, and because reviews never reached the questions file, so the run could not use them.
26. Replayed the 79 saved answers through four citation checks, without any new model calls. The production check showed 15 answers. Placing the missing `[n]` marker ourselves, after the sentence that best matches the quote, showed 75, and every made-up quote stayed blocked. The AI judge graded 51 of the 60 rescued answers correct, 5 partly correct and 4 wrong, and one of the wrong ones answers a question the notes cannot answer. We did this to find out whether the blocked answers were bad answers or good answers with a missing marker. Most were good, so the marker rule, not the model's knowledge, is what hides answers from students. We did not change `apps/api`. The 4 wrong answers show that a quote check cannot tell whether an answer fits the question, so a fix also needs an on-topic check.
